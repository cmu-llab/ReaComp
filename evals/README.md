# Evaluation Outputs

This directory contains evaluation artifacts generated by `scripts/run_eval.sh`.

## Files

| File | Description |
|------|-------------|
| `eval.csv` | Per-instance metrics table (one row per task across all runs) |
| `reward_hist.png` | Distribution of best-reward scores per run |
| `pass_rate_by_dataset.png` | Pass rate (reward = 1.0) broken down by source dataset |
| `mean_reward_by_dataset.png` | Mean best-reward broken down by source dataset |
| `iter_breakdown.png` | Which reward-loop iteration first achieved a perfect score |
| `blame_heatmap.png` | Blame-sequence distribution across runs |
| `cost.png` | Per-task total_cost and objective distributions |
| `library_reuse_rate.png` | CREATE vs REUSE event counts per run (from `.ckpt.json`) |
| `library_growth.png` | Cumulative library size over log events (from `.ckpt.json`) |

## Metric Definitions

### Reward & Loss

| Metric | Description |
|--------|-------------|
| `best_reward` | Best reward achieved across all reward-loop iterations (0–1). 1.0 = fully correct. |
| `task_loss` | `1 - best_reward`. Contribution to the session's task-loss sum. |
| `solved` | 1 if `best_reward >= 1.0`, else 0. Used for pass-rate calculations. |

### Reward Loop

The agent runs up to `--max-reward-iters` iterations (default 3) per task. After each iteration the reward function scores the solution and the agent can retry.

| Metric | Description |
|--------|-------------|
| `num_iters` | Number of reward-loop iterations actually run for this task. |
| `first_perfect_iter` | 0-based index of the first iteration with reward = 1.0. `None` if never solved. |

### Blame

After each iteration, the BCR agent (or executor) is assigned a **blame** label explaining why the reward was not 1.0:

| Blame | Meaning |
|-------|---------|
| `execution` | The solution code raised a runtime exception — the executor could not produce a result at all. |
| `library` | Code ran successfully but used a library function and still scored < 1.0 — the library function may be wrong or mis-applied. |
| `partial` | Code ran and produced a result, but the reward was between 0 and 1 — logically close but not exact. Used for both `direct`-action answers and `solve`-action code. |
| `logic` | Code ran and produced a result with reward = 0 — completely wrong output (currently unused, maps to `partial`). |

### Blame Sequence Heatmap

The **blame heatmap** shows the distribution of blame *sequences* across runs.
A blame sequence is the concatenation of per-iteration blame labels separated by `→`, e.g.:

- `partial` — solved on first try (or never retried, score was 0)
- `partial→partial` — two iterations, both partial credit, second may or may not be perfect
- `execution→partial` — first attempt crashed, second got partial credit
- `(no retries)` — only one iteration was run and no reward history was recorded

Each cell shows the fraction of tasks in that run with that blame sequence. Common patterns:

- **High `partial` (single-iter)** — most tasks solved immediately on first attempt.
- **High `partial→partial→partial`** — agent is stuck, same partial answer across all retries (e.g., trailing punctuation issue, or a function the agent cannot improve).
- **High `execution→...`** — the library function or generated code is consistently crashing.

### Cost Metrics

These come from `CostTracker` (see `symbolic_agent/costs.py`):

| Metric | Formula | Description |
|--------|---------|-------------|
| `num_new_functions` | — | Total functions created in the library during this session. |
| `total_function_length` | — | Sum of line counts across all created functions. |
| `reuse_count` | — | Total number of library function reuse events across all tasks. |
| `redundancy_penalty` | `γ · Σ sim(f_i, f_j)` for pairs with sim > 0.8 | Penalises structurally similar function pairs (AST-based, see below). γ = 2.0. |
| `reuse_reward` | `δ · Σ log(1 + uses_i)` | Rewards reusing functions. δ = 0.5. |
| `total_cost` | `α·N + β·L + γ·Rpen − δ·Rrew` | Full library complexity cost. α=1.0, β=0.05. |
| `objective` | `task_loss + λ·total_cost` | Combined objective (lower is better). λ = 0.3. |
| `redundancy_mode` | — | Algorithm used: `ast_jaccard` or `edit_distance` (see `--redundancy-mode`). |

#### Redundancy penalty modes (`--redundancy-mode`)

**`ast_jaccard`** (default): `sim = max(Jaccard(node_type_sets), Jaccard(callee_name_sets))`. Captures structural shape (A) and shared function dependencies (B). O(N²) pairs, O(n) per function.

**`edit_distance`**: `sim = 1 − normalised_edit_distance(DFS_node_sequence_i, DFS_node_sequence_j)`. More sensitive to ordering; O(m·n) per pair.

#### Why redundancy penalty ≠ reuse reward

These terms are complementary, not redundant:
- **Redundancy penalty** is a *static structural* property: fires when two function *definitions* implement similar logic (duplicate code). Does not depend on how often functions are called.
- **Reuse reward** is a *dynamic behavioural* property: measures how often existing functions are actually *used* across tasks. A library with 50 unique functions each used once has zero redundancy but low reuse reward.

A healthy library has low redundancy **and** high reuse. Both terms are needed — redundancy alone cannot detect under-utilisation, and reuse reward alone cannot detect structural duplication.

### Library Panels (ckpt-based)

These panels are generated from the `.ckpt.json` files saved alongside each output JSONL.

**`library_reuse_rate.png`** — For each run: number of `[CREATE]` events (new functions written) vs `[REUSE]` events (existing functions called). High reuse rate = good generalisation of library functions across tasks.

**`library_growth.png`** — Line chart of cumulative function count vs. log-event index. A flat line after an initial rise means the library stabilised and later tasks all reused existing functions (ideal). A steadily rising line means the agent keeps creating task-specific functions instead of reusing.

## Experiments

### `pbebench_lite` (n=50)
PBEBench-Lite tasks: infer string transformation programs from input/output examples.
- Pass rate: 80.0% | Mean reward: 0.916
- Library: 1 function (`infer_replace_programs`), reused 157 times — extreme reuse.

### `reasoning_gym_easy` (n=64)
Basic arithmetic (18) + caesar_cipher (8) + symbolic (38) tasks from reasoning-gym.
- Pass rate: 87.5% | Mean reward: 0.983
- Weakness: caesar_cipher at 12.5% pass (trailing-punctuation issue in BCR direct-mode).
- Library: 5 functions, 194 reuse events (97.5% reuse rate).

### `pbebench_rg_string` (n=100, interleaved)
50 PBEBench + 50 reasoning-gym `string_manipulation` tasks interleaved round-robin.
- Pass rate: 87.0% | Mean reward: 0.922
- Library: 46 functions, only 209 reuse events (81% reuse rate) — low reuse, many near-duplicate task-specific functions created. See architecture diagnosis notes.
